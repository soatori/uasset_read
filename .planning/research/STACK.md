    uint8 bIsReference : 1;
    uint8 bIsConst : 1;

    uint8 bIsSTEAM : 1;                // Single/Time/Event/Multi

**Python 对应 dataclass：**

```python
from dataclasses import dataclass
from typing import List, Optional

@dataclass
class UEdGraphPin:
    """节点引脚 - UE 二进制序列化格式"""
    pin_name: str                      # FString -> str
    pin_type: "FEdGraphPinType"        # 已实现于 Phase 3
    default_value: Optional[str] = None
    auto_default_value: Optional[str] = None
    linked_to: List["UEdGraphPinRef"] = field(default_factory=list)
    
    # 序列化标志
    not_connectable: bool = False
    default_value_readonly: bool = False
    is_reference: bool = False
    is_const: bool = False
    is_weak_pointer: bool = False
    is_uproperty: bool = False
    
    # 解析时参考字段（非序列化）
    owning_node: Optional["K2Node"] = None  # 链接解析后填充
```

**序列化顺序（UEdGraphPin.cpp lines 163-346）：**

```
1. PinName (FString)
2. PinType (FEdGraphPinType - 已实现)
3. AutoGenDefaultValue (FString)
4. LinkedTo 数组
   a. Count (int32)
   b. 每个 UEdGraphPin* (指针编码，见下文)
5. SerializedFlags (uint8)
   bNotConnectable, bDefaultValueIsReadOnly, bIsReference, bIsConst
6. (可选) AdditionalFlags (UE5+, bitfield)
```

## 关键问题：节点引用编码

### Elasticsearch 指针编码（核心难点）

**问题：** UEdGraphPin::LinkedTo 存储的是 `UEdGraphPin*` 指针，在序列化时不能直接保存指针值。

**UE 解决方案（来自 UE 源码论坛讨论）：**

UE 在序列化图数据时使用**相对引用**或**名称查找**，而非直接指针：

```cpp
// UEdGraphPin 序列化示例（简化）
void UEdGraphPin::Serialize(FArchive& Ar)
{
    Super::Serialize(Ar);
    
    Ar << PinName;
    Ar << PinType;
    Ar << AutoGenDefaultValue;
    
    // LinkedTo 序列化 - 关键！
    if (Ar.IsLoading())
    {
        // 加载时：先序列化数量，再查找
        int32 NumLinks;
        Ar << NumLinks;
        for (int32 i = 0; i < NumLinks; ++i)
        {
            // 方式 1: 通过名称查找（推荐）
            FString LinkedPinName;
            Ar << LinkedPinName;
            
            // 方式 2: 通过索引（旧版）
            // int32 LinkedPinIndex;
            // Ar << LinkedPinIndex;
            
            // 查找后建立链接
        }
    }
    else if (Ar.IsSaving())
    {
        // 保存时：序列化名称或索引
        Ar << LinkedTo.Num();
        for (UEdGraphPin* Pin : LinkedTo)
        {
            if (Pin)
            {
                Ar << Pin->PinName;  // 序列化名称用于查找
            }
        }
    }
}
```

### 确定的序列化策略

根据搜索结果和 UE 模式，**LinkedTo** 的序列化有以下确定的策略：

| 方式 | 条件 | 格式 | 推荐 |
|------|------|------|------|
| **名称索引** | UE4/UE5 现代 | `int32 Count + FString[Count]` | ✓ 推荐 |
| **索引索引** | 旧版 UE4 | `int32 Count + int32[Index]` | |
| **GUID 索引** | 某些子类 | `int32 Count + FGuid[Count]` | |

**建议采用名称索引**，因为：
1. 最稳定（跨版本）
2. 易于调试
3. 无需维护外部索引表

## 零新增依赖

**重要结论：不需要任何新的运行时依赖。**

现有技术栈已完整覆盖蓝图图解析需求：

| 需求 | 已有技术 | 说明 |
|------|----------|------|
| 二进制读取 | struct | u32/i32/i64/f32/f64 |
| 字符串 | read_fstring() | FString -> Python str |
| FName 索引 | read_name() | NameMap 索引 |
| 数组 | 循环 + count | TArray 序列化 |
| 引用 | 链接后解析 | LinkedTo → pin_name |

**无需添加：**
- ❌ construct（声明式解析器）
- ❌ pydantic（验证开销）
- ❌ numpy（非数值解析）
- ❌ any circuit بأن

## 不推荐添加的内容

### 1. C++ 扩展

**_reason:** Python 性能足够（单文件解析 <100MB），且违背零依赖原则。

### 2. 自定义二进制格式

**reason:** .uasset 已是二进制；解析器只需读取，无需输出二进制。

### 3. 第三方反序列化库

**reason:** 
- construct 等增加复杂性
- 性能提升微乎其微（解析是瓶颈）
- 维护负担大

### 4. 数据库或缓存层

**reason:** 
- 蓝图解析是单次任务
- 内存足够Fast（<500MB）
- 增加部署复杂性
