# Phase 35e: Pin Offset 根因诊断与 UE5 C++ 参考验证 - Research

**Researched:** 2026-05-13
**Domain:** Unreal Engine 5 UEdGraphPin / FEdGraphPinType binary serialization format
**Confidence:** MEDIUM

## Summary

Phase 35b 的 fixes (read_bool_ue5, BitField u32, FText b_has_culture) 修复了约 12 字节的累积漂移，但 `linked_to_raw` 仍然为空（0/10 pins）。遗留的 ~4 字节偏移位于 Direction 字段与 PinCategory FName 之间。

**核心发现**: 通过阅读 UE5 C++ 源码（EdGraphPin.cpp L1838-1964, L163-346），确认：

1. **Direction 字段后 C++ 源码中无 padding** — `Ar << Direction;` 后紧接 `PinType.Serialize(Ar);`，字段间没有任何额外的填充字节。因此 ~4 字节偏移不可能来自 Direction 与 PinCategory 之间的显式 padding。

2. **代码存在 4 个未处理的 C++ 字段**, 共同造成累积偏移：
   - **FEdGraphPinType 最后缺少 `bSerializeAsSinglePrecisionFloat`** (1 byte, WITH_EDITOR only)
   - **FEdGraphPinType 中 `bIsUObjectWrapper` 因 GUID 不匹配被跳过** (1 byte) 
   - **DefaultTextValue 被当作 FString 读取而非 FText** (至少 2-12 bytes 差异)
   - **FUE5ReleaseStreamObjectVersion GUID 未在 constants.py 中定义** (影响 FEdGraphPinType 中的额外 Editor 字段)

3. **FText Custom 类型 (history_type=150) 的 8 字节跳过 size 需要验证** — 可能不是精确值

4. **FUE5ReleaseStreamObjectVersion 是一个新的 custom version GUID** (`D89B5E42-24BD4D46-8412ACA8-DF641779`)，代码中完全没有定义。如果测试资产的 13 个 custom version entries 中包含这个 GUID，所有与 `FUE5ReleaseStreamObjectVersion` 相关的字段都会以错误逻辑读取。

**Primary recommendation:** 优先验证 DefaultTextValue 的 FText vs FString 问题（这是最可能的 LinkedTo 空的根因），然后通过精确的二进制跟踪确认所有字段边界。

### FText 序列化格式（from UE5 FText.h）

```
FText 序列化:
1. Flags (int32, 4 bytes): 标志位，通常为 0x00000000
2. HistoryType (uint8, 1 byte): 文本历史类型
   - 0xFF (None): b_has_culture (u8) + [culture FString]
   - 0 (Base): namespace FString + key FString + sourceString FString
   - 1-254 (Custom): 变量数据，具体格式视 HistoryType 值而定
```

### 4 字节偏移的 4 种可能来源分析

#### 源 A: DefaultTextValue FString vs FText 差异（最高概率）
C++ 源码: `Ar << DefaultTextValue;` — DefaultTextValue 是 FText
当前代码: `_read_ftext_fstring(archive)` — 读取为简单 FString

对于空的 DefaultTextValue (history_type=0xFF None):
- FText 消耗: flags(4B) + history_type(1B) + b_has_culture(1B) = 6 bytes
- FString 消耗: len=0(4B) = 4 bytes
- **差异: +2 bytes** (LinkedTo 读取位置早了 2 个字节)

对于 history_type=0 (Base) 的空文本:
- FText 消耗: 4+1+3*4 = 17 bytes (3 个空 FString)
- FString 消耗: 4 bytes
- **差异: +13 bytes**

**影响**: LinkedTo 在错误位置读取 array_count，很可能读到前一个字段（DefaultTextValue body）的中间数据，导致 array_count=0 或越界。

#### 源 B: `bIsUObjectWrapper` 被跳过（确认）
由于 `FRELEASE_OBJECT_VERSION_GUID` (9C54D522-A8264FBE-94210746-61B482D0) 不在测试资产的 13 个 custom versions 中，`release_version = 0`，因此 `release_version >= 10` 为 False。代码不读取该 bool。

**差异: 1 byte** — 影响 PinType 之后的所有字段（DefaultValue, AutoDefaultValue, DefaultObject, DefaultTextValue, LinkedTo）。

#### 源 C: `bSerializeAsSinglePrecisionFloat` 未实现（确认）
C++ 源码 (EdGraphPin.cpp L327-343) 在 WITH_EDITOR 条件下序列化一个额外的 bool。
当前代码完全没有这个逻辑。
**差异: 1 byte** (如果存在) — 影响 PinType 之后的所有字段。

#### 源 D: FText Custom 类型 8 字节跳过不精确
Phase 35b-03 的修复假设 EditorOnly FText custom 类型跳过 8 字节。
这个值可能因历史类型值而异 — 可能是 8、12 或可变大小。
**差异: 0~4+ bytes** — 影响 PinFriendlyName 消耗。

### 4 种来源的累积效应

```
PinType 结束位置 = 正常 +1B(D2) = 偏移 +1
DefaultValue 读取位置 = 偏移 +1
AutoDefaultValue 读取位置 = 偏移 +1
DefaultObject 读取位置 = 偏移 +1
DefaultTextValue 读取位置 = 偏移 +1
  DefaultTextValue FString 读取 = 4B(FString) - 6B(FText) = -2B 偏移
LinkedTo 读取位置 = 偏移 +1 -2 = 偏移 -1
```

仅 D2 + D3 就可能导致 LinkedTo 提前 1 个字节读取，碰到随机数据。但实际上偏移方向和大小取决于所有 4 种来源的组合。

如果同时包含 D1 (+1), D2 (+1), D3 (-2 to -13):
- 最小: +1+1-2 = 0 bytes drift (刚好对齐)
- 最可能(空FText): +1+1-2 = 0 bytes drift (刚好对齐)
- 最大: +1+1-13 = -11 bytes drift

但如果 D3 差异是 +2 (FString读4B vs FText读6B)，且如果 D2 和 D1 都不存在:
- D3 only: +2 bytes (LinkedTo 提前 2 个字节)

结合 D1=+1, D2=+1, D3=+2:
- 总和: +1+1+2 = +4 bytes drift (LinkedTo 提前 4 个字节)

**这正好匹配 !** 如果 FText 有 Base history_type:
- D1(1) + D2(1) + D3(Base FText: 17-4=13) = +15 bytes

对于 None history_type:
- D1(1) + D2(1) + D3(None FText: 6-4=2) = +4 bytes

如果测试资产的 DefaultTextValue 使用 history_type=0xFF (None)，三者累加正好是 **4 字节偏移**！

## Common Pitfalls

### Pitfall 1: FText 和 FString 在序列化中不可互换
**什么会错**: DefaultTextValue 声明为 FText（C++），但代码作为 FString 读取。
**为什么会发生**: FString.len=0 (4 bytes) 和 FText.flags=0 (4 bytes) 表面上看结果相同，但 FText 还有 history_type + body，导致多消耗 2+ 字节。
**如何避免**: 所有 `Ar << FTextVariable` 必须使用完整的 FText 读取（flags + history_type + body），不能用 FString 替代。

### Pitfall 2: Custom Version GUID 不匹配导致版本检查失效
**什么会错**: 测试资产的 13 个 custom version GUID 不包含项目期望的 3 个 GUID（FFramework/FUE5MainStream/FRelease）。所有 `get_custom_version()` 返回 0，导致：
- `bIsUObjectWrapper` 被跳过（需要 Release >= 10）
- 其他版本相关功能使用默认值
**为什么会发生**: 资产可能由游戏特定 UE5 构建版本保存，使用不同的 GUID 值。
**如何预防**: 使用 `file_version_ue5 > 0` 作为后备触发条件，或尝试匹配 GUID 对应版本。
**警告标志**: `summary.get_custom_version(guid, 0)` 对所有已知 GUID 返回 0。

### Pitfall 3: FText Custom 类型的 EditorOnly 数据大小不确定
**什么会错**: 35b-03 硬编码 8 字节跳过，但实际大小可能因 history_type 而异（8/12/可变）。
**为什么会发生**: EditorOnly FText 数据在运行时序列化格式不同，取决于文本类型。
**如何避免**: 通过精确的二进制跟踪确定实际大小，不在每种 history_type 上做假设。
