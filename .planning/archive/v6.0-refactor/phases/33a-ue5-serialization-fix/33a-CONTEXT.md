# Phase 33a: UE5 序列化问题修复 - Context

**Gathered:** 2026-05-12
**Status:** Creating context for new phase

## Phase Boundary

修复 UE5 蓝图序列化格式解析中的已知问题，针对从 UE5.0 (UE5=1017) 蓝图文件 `BP_FirstPersonCharacter.uasset` 中发现的以下错误：

### 已识别问题

1. **数组大小验证失败** - `CategoryName` 属性读取 3328 字节，但文件仅余 2300 字节
2. **负数大小错误** - `RelativeLocation` 属性读取到 `-1067974656` (0xBFC00000)
3. **FText 字符串过大** - `DefaultTextValue` 字段读取到 33554432 字符长度

### 问题定位

所有错误都出现在第 1577058304 和第 3224633344 导出体中，这些是 SCS_Node 和 SkeletalMeshComponent 类型的编译时生成节点。

**不包含：** 不修复旧版 uasset_read.py 的问题，不引入新功能，仅修复 UE5 序列化格式解析的兼容性问题。

## Implementation Decisions

### 问题分类

| 问题类型 | 严重性 | 影响范围 | 修复优先级 |
|---------|--------|---------|-----------|
| FText 长度过大 | MEDIUM | Kubernetes 节点的 DefaultTextValue/AutogeneratedDefaultValue 字段 | HIGH |
| 负数大小 (0xBFC00000) | HIGH | CharacterMesh0 的 RelativeLocation 属性，导致后续所有偏移错位 | CRITICAL |
| 数组大小验证失败 | MEDIUM | SCS_Node 的 CategoryName 属性 (Warning 类型) | MEDIUM |

### 修复策略

#### D-01: 根本原因分析优先
**原因：** 三个错误可能由同一个序列化偏移错位引起，直接修复症状可能掩盖根本问题。

**计划：**
1. 创建调试脚本 `tools/debug_ue5_serialization.py` 记录每个属性的读取偏移和大小
2. 对比 UE5.0 原版序列化格式（从 UE5.0 源码或已知正确解析的资产）
3. 确定偏移错位的精确位置和原因

#### D-02: 分层修复
**原因：** 修复需要逐步验证，避免引入新问题。

**计划：**
1. **Phase 33a-01:** 修复 FText 序列化格式（针对 history_type=255 的 None 类型）
2. **Phase 33a-02:** 修复 PropertyTag 大小验证逻辑（增加容错模式）
3. **Phase 33a-03:** 修复节点序列化顺序检测（解决偏移错位）

#### D-03: 代码位置
**原因：** 问题涉及底层序列化解析。

**决定：**
- `serializers/graph.py` — 修复 Pin 序列化中的 FText 读取
- `serializers/property_tags.py` — 修复 PropertyTag size 验证
- `serializers/object_resources.py` — 修复导出体序列化偏移计算
- 新建 `serializers/ue5_fixes.py` — UE5 特定修复逻辑（如有必要）

#### D-04: 容错 vs 修复
**原因：** 部分错误可能是数据损坏而非格式不兼容。

**决定：**
- **容错模式（默认）：** 捕获异常，返回空/默认值，记录 Warning
- **严格模式（调试）：** 抛出异常，打印详细调试信息（通过 `--debug-strict` CLI 标志启用）

### 基于现有代码的修复

#### 问题 1: FText history_type=255 (None 类型)

**旧版代码 (uasset_read.py):**
```python
# FText 有多种 history_type:
# -1 (0xFF): None (无历史)
# 0 (0x00): Base (基础命名空间)
# 其他: 自定义历史
```

**当前新版代码 (archive.py read_fstring):**
```python
def read_fstring(self) -> str:
    length = self.read_i32()
    if length == 0:
        return ""
    if length < 0:
        utf16_len = -length * 2
        if utf16_len > 10_000_000:
            raise ParseError(f"UTF-16 string length {utf16_len} too large")
        # ... UTF-16 解码
```

**修复：** FText 不使用 read_fstring，需要专门的 read_fstring_with_history() 函数。

#### 问题 2: SerializedProperty Size 验证

**当前代码 (archive.py validate_size):**
```python
def validate_size(self, size: int, context: str = "") -> None:
    if size < 0:
        raise ParseError(f"Invalid size {size} (negative) at {context}")
    current_pos = self.tell()
    remaining = self._file_size - current_pos
    if size > remaining:
        raise ParseError(f"Size {size} exceeds remaining {remaining} bytes at {context}")
    max_reasonable = max(1024, min(self._file_size // 10, 100 * 1024 * 1024))
    if size > max_reasonable:
        raise ParseError(f"Size {size} exceeds max_reasonable {max_reasonable}")
```

**问题：** `max_reasonable` 验证对 UE5 编译节点可能过于严格。

**修复：** 对 `Warning` 类型属性跳过 max_reasonable 验证（警告信息本身就是异常标记）。

#### 问题 3: PropertyTag size 与 SerialSize 不一致

**当前代码 ( serializers/property_tags.py read_property_tag):**
```python
def read_property_tag(archive, name_map, legacy_version, ue5_version):
    # 读取 PropertyTag 结构
    # ...
    tag.size = archive.read_i64()  # or i32 for legacy
    # ...
```

**问题：** UE5 可能在 size 后添加额外的对齐或元数据字段。

**修复：** 添加 `ue5_property_tag_extensions` 容错解析。

## Specific Ideas

### Idea 1: 创建 UE5 序列化调试器

**目标：** 记录所有 PropertyTag 的读取过程

```python
# tools/debug_ue5_serialization.py
def debug_property_tag_reading(archive, name_map, version):
    """记录每个 PropertyTag 的偏移、大小、类型、读取后位置"""
    start_pos = archive.tell()
    tag = read_property_tag(archive, name_map, version)
    end_pos = archive.tell()
    
    print(f"[{hex(start_pos)}] {tag.name}: type={tag.type}, size={tag.size}, read={end_pos-start_pos}")
    
    return tag
```

### Idea 2: 容错 PropertyTag 读取器

**目标：** 对异常大小的 PropertyTag 采用 fallback 读取

```python
def read_property_tag_fallback(archive, name_map, legacy_version, ue5_version):
    """读取 PropertyTag，对异常大小采用容错策略"""
    try:
        return read_property_tag(archive, name_map, legacy_version, ue5_version)
    except ParseError as e:
        # 检查是否是 Warning 类型（表示数据异常）
        if "Warning" in str(e):
            # 记录警告但继续
            return PropertyTag(
                name="Warning",
                type="Warning",
                size=0,
                # ... 其他字段设置为默认值
            )
        raise
```

### Idea 3: UE5 版本检测和分支

**目标：** 根据 UE5 版本选择正确的序列化逻辑

```python
def get_ue5_serialization_mode(ue5_version):
    """确定 UE5 版本对应的序列化模式"""
    if ue5_version >= 1011:  # UE5.0+
        return "ue5.0_plus"
    elif ue5_version >= 1000:
        return "ue5.0"
    else:
        return "ue4_compatible"

def read_property_tag_for_ue5(archive, name_map, version):
    mode = get_ue5_serialization_mode(version.file_version_ue5)
    
    if mode == "ue5.0_plus":
        return read_property_tag_ue5_0_plus(archive, name_map, version)
    else:
        return read_property_tag(archive, name_map, version)
```

## Common Pitfalls

### Pitfall 1: 修复引入新错位

**What goes wrong:** 修复 FText 读取后，后续数据偏移仍不正确。

**Why it happens:** 可能还有其他字段也使用了 FText 格式但未修复。

**How to avoid:** 使用调试脚本比较修复前后所有偏移，确保每个 PropertyTag 读取后的位置与预期一致。

### Pitfall 2: 过度容错掩盖数据损坏

**What goes wrong:** 容错逻辑太宽松，导致损坏的数据被静默忽略。

**Why it happens:** `except Exception: pass` 太宽泛。

**How to avoid:** 
- 容错需记录具体原因到 `result.errors`
- 添加 `--debug-strict` 模式在开发时抛出异常

### Pitfall 3: 版本分支过多导致维护困难

**What goes wrong:** 为每个 UE5 版本添加单独的分支，代码难以维护。

**Why it happens:** UE5.0, 5.1, 5.2 的序列化格式略有不同。

**How to avoid:** 
- 优先修复最常见的 UE5.0 (UE5=1017)
- 使用配置驱动的序列化策略（ Version -> Serializer 映射表）
- 添加测试矩阵覆盖多个 UE5 版本
